## 브랜치 3종

| 브랜치 | 역할 | 여기서 직접 작업하나요? |
|---|---|---|
| `prod` | **실제 배포되는 코드**. 사용자가 보는 것과 같음 | ❌ 절대 안 됨 |
| `main` | 배포 직전 상태. 검토가 끝난 것만 모임 | ❌ 안 됨 |
| `dev` | 개발 통합. 만든 기능들이 여기 모여서 서로 잘 도는지 확인 | ❌ 직접 말고 병합으로 |
| `feature/*` | **실제 작업 공간**. 기능 하나당 하나씩 | ✅ 여기서 작업 |

## 흐름

```
feature/cat-note-db  ─┐
feature/cat-note-api ─┼─→  dev  ─→  main  ─→  prod  →  🚀 배포
feature/partner-select ┘
      (작업)          (합쳐서 확인)  (검토 완료)  (배포)
```

## 작업 순서 (매번 이대로)

### 1. 새 작업 시작 — dev에서 가지 치기

```bash
git checkout dev
git pull
git checkout -b feature/cat-note-db
```

> 💡 **항상 `dev`에서 시작**해요. `prod`에서 가지를 치면 남들이 만든 최신 코드가 없어서 나중에 충돌나요.

### 2. 작업하고 커밋

```bash
git add .
git commit -m "feat: 고양이 수첩 테이블 8개 추가"
```

### 3. 올리기

```bash
git push -u origin feature/cat-note-db
```

### 4. dev에 합치기

```bash
git checkout dev
git merge feature/cat-note-db
git push
```

> 회사처럼 하려면 이 단계를 **PR(Pull Request)**로 해요. 깃허브에서 `feature/... → dev`로 PR을 만들고, 스스로 코드를 한 번 훑어본 뒤 머지하면 돼요. 혼자 해도 "내가 뭘 바꿨는지" 다시 보게 돼서 실수를 잘 잡아요.

### 5. 작업 끝난 가지 지우기

```bash
git branch -d feature/cat-note-db
git push origin --delete feature/cat-note-db
```

### 6. 배포할 때 (기능이 어느 정도 모이면)

```bash
git checkout main && git merge dev && git push
git checkout prod && git merge main && git push
```

## 브랜치 이름 규칙

| 앞머리 | 언제 | 예시 |
|---|---|---|
| `feature/` | 새 기능 | `feature/partner-select` |
| `fix/` | 버그 고치기 | `fix/streak-count` |
| `docs/` | 문서만 | `docs/api-spec` |
| `chore/` | 설정·정리 | `chore/eslint-config` |

## 커밋 메시지 규칙 (Conventional Commits)

```
feat: 짝꿍 선택 화면 추가
fix: 연속 기록이 하루 밀려 세지던 문제 수정
docs: API 명세서에 친구 검색 추가
chore: 린트 설정 정리
```

앞머리만 붙이면 돼요. 나중에 `git log --oneline`으로 볼 때 뭐가 기능이고 뭐가 수정인지 한눈에 보여요.

## ⚠️ 주의: 프론트 배포는 저장소가 따로예요

`prod`에 합쳐도 **사이트에 바로 반영되지 않아요.** 실제 배포는 이 흐름이에요:

```
headache-log (prod)  →  world-holicat-frontend (main)  →  Vercel  →  www.world-holicat.com
                     ↑ 여기서 파일을 복사해 옮겨야 함
```

백엔드는 `world-holicat-backend`의 GitHub Actions로 배포돼요.

> 📌 나중에 이 복사 과정을 자동화하면 편해요 (GitHub Actions).
